# Lua 5.4.9 vs 5.5.1 — differences relevant to rustynail

Derived from the vendored trees (`vendor/lua-5.4`, `vendor/lua-5.5`) on 2026-10-27, plus observed behavior of
`ref/54/build/lua` and `ref/55/build/lua`. **Authoritative list of what is version-specific.** Extend it whenever a builder
finds another delta; never rely on memory of either version. "VERIFIED" = checked in vendored source/binary this session;
"TO CHECK" = from the Opus review or memory, must be confirmed in source before relying on it.

## Size of the diff (changed lines, `diff 5.4 5.5`)
lvm 579 · lparser 765 · lcode 391 · ltable 1196 · lgc 808 · lobject 326 · lstring 123 · lstate 194 · ldo 540 · ldebug 100 · lstrlib 305
(total C: 24,736 lines in 5.4.9 vs 26,423 in 5.5.1). `ltable`, `lparser`, `lgc`, `lvm`, `ldo` differ substantially ⇒ forked modules.

## Bytecode / compiler (VERIFIED)
- 5.4: 83 opcodes; 5.5: **85**. New in 5.5: **`GETVARG`**, **`ERRNNIL`**. `SHRI`/`SHLI` ordering differs between versions.
- 5.5 `lopcodes.h` adds `SIZE_vB = 6`, `SIZE_vC = 10` (extended-field iABC variants). Re-read `lopcodes.h` for the exact layouts.
- `LUAC_VERSION`: 5.4 = `(504/100)*16 + 504%100`; 5.5 = `MAJOR_N*16 + MINOR_N`. Same numeric result, but chunk contents are not interchangeable. `LUAC_FORMAT` = 0 in both.
- TO CHECK: `global` declarations (contextual keyword under `LUA_COMPAT_GLOBAL`), named varargs `function f(...t)`, read-only for-loop control variable, numeric `for` stack slot count, `table.create`.

## Numbers and strings (VERIFIED)
- `tostring(1/3)`: 5.5 → `0.33333333333333331`, 5.4 → `0.33333333333333`. `math.pi`: 5.5 → `3.1415926535897931`, 5.4 → `3.1415926535898`.
  5.5 uses `%.15g` then `%.17g` when it does not round-trip (TO CHECK exact logic in `lobject.c:tostringbuff`/`lua_numbertocstring`).
- 5.4 reference has `math.pow` (via `LUA_COMPAT_5_3`); 5.5 does not.

## GC (VERIFIED unless marked)
- Library default `g->gckind = KGC_INC` in both (`lstate.c`); **`lua.c` calls `lua_gc(L, LUA_GCGEN…)` at startup in both** ⇒ reference `lua` runs generational. rustynail's CLI must do the same.
- TO CHECK: `collectgarbage("setpause"/"setstepmul")` removed in 5.5 in favor of `"param"` (`LUA_GCPARAM`, `LUA_GCP*`); `LUA_GCGEN`/`LUA_GCINC` constant values differ.

## C API (VERIFIED by symbol diff of `lua.h` + `lauxlib.h`)
- Only in 5.5: `luaL_alloc`, `luaL_makeseed`, `lua_numbertocstring`, `lua_pushexternalstring`.
- Only in 5.4: `lua_setcstacklimit` (removed in 5.5). (Other names in the raw diff are macros/internal.)
- TO CHECK: `lua_newstate` gains a `seed` argument in 5.5; `luaL_openlibs` → macro over `luaL_openselectedlibs`; `lua_resetthread` macro; `lua_Debug` fields (`extraargs`, `ftransfer`/`ntransfer` types); `LUA_RIDX_MAINTHREAD`; `LUA_REGISTRYINDEX` value; `LUAI_MAXSTACK` no longer public in 5.5.
- Same in both: `LUA_EXTRASPACE = sizeof(void*)`, `LUA_IDSIZE = 60`, `LUAL_BUFFERSIZE = 16*sizeof(void*)*sizeof(lua_Number)`, `lua_getextraspace(L) = (char*)L - LUA_EXTRASPACE`.

## Reference build (VERIFIED)
- 5.4.9 Makefile: `CFLAGS = -O2 -Wall -Wextra -DLUA_COMPAT_5_3`. 5.5.1 Makefile: `CFLAGS = -O2 -Wall -Wextra`.

## Front end 5.4.9 vs 5.5.1: observed differences (A3, all VERIFIED against `ref/54` and `ref/55` by byte-identical listings/dumps)
Line refs are in `vendor/lua-5.4/src` ("5.4") and `vendor/lua-5.5/src` ("5.5").

### Lexer (llex.c / llex.h)
- Reserved words: 5.5 adds `global`, but with `LUA_COMPAT_GLOBAL=1` (default) it is returned as a plain name and recognised contextually in `statement` (5.5 lparser.c 2117-2131, `ls->glbn`). 5.4 has no `global` at all: it is an ordinary identifier (`global = 1`, `global.x`, `global(1)`, `global x` is a plain syntax error). 5.5 also keeps `brkn` ("break") in `LexState`; 5.4 builds the string on demand.
- Everything else in the lexer (numerals, escapes, error text, `chunkid`) is identical; only buffer growth (`luaZ_resizebuffer` 1.5x vs 2x) and string anchoring differ and are not observable.
- `luaK_semerror` (5.4 lcode.c:47): sets token to 0 and reports at the *current* `linenumber`; 5.5 (lcode.c:43) also resets `ls->linenumber = ls->lastline`, so semantic errors in 5.5 are reported at the line of the last consumed token.
- Both versions: `lexerror` adds "near <token>" only `if (token)`, so a NUL byte (token 0) in the source gives e.g. `stdin:1: unexpected symbol` with no "near" (found by the parser differential, STATUS.md "Parser differential"; fixed in the shared `lexer.rs`). The parser differential (~25M cases per version: messages, dumps, listings, binary chunks) found no other difference in either version.

### Binary chunks (ldump.c / lundump.c / lundump.h)
- Header: 5.4 = sig, `0x54`, format 0, `LUAC_DATA`, then **only** 3 size bytes (`Instruction`=4, `lua_Integer`=8, `lua_Number`=8), then `LUAC_INT = 0x5678` as a raw 8-byte integer and `LUAC_NUM = 370.5` raw (lundump.h:18-19). 5.5: `0x55`, each of `int`, `Instruction`, `lua_Integer`, `lua_Number` is size byte + value, constants are **negative** (`-0x5678`, `-370.5`), plus `LUAC_INST`. Size-mismatch messages: 5.4 `"Instruction size mismatch"`, `"lua_Integer size mismatch"`, `"lua_Number size mismatch"`, `"integer format mismatch"`, `"float format mismatch"` (lundump.c 285-305).
- Sizes (`dumpSize`, ldump.c:65): 5.4 stores 7-bit groups most-significant first with the **high bit set on the last byte** (loader loop `while ((b & 0x80) == 0)`, overflow test `x >= limit` before shifting); 5.5 sets the high bit on every byte except the last and uses `x > limit`. Strings: 5.4 `size+1` then the bytes with **no trailing NUL** and 0 for NULL; 5.5 writes the NUL and has back-references to earlier strings (`0, index`).
- Integers/floats: 5.4 raw 8-byte little-endian; 5.5 zig-zag varint for `lua_Integer`, raw for floats.
- Function body order: 5.4 `source, linedefined, lastlinedefined, numparams, is_vararg, maxstacksize, code, k, upvalues, protos, debug`; source is `NULL` when stripped or equal to the parent's source (child inherits the parent's on load, so every `ProtoData.source` is set after undump); 5.5 puts `source` after `protos` and always writes it unless stripped. 5.4 `is_vararg` is a plain byte (0/1); 5.5 stores `Proto.flag` (`PF_VAHID|PF_VATAB`).
- No alignment padding in 5.4 (5.5 aligns code and abslineinfo to 4). 5.4 abslineinfo = two varint sizes `(pc, line)` per entry; 5.5 writes raw 8-byte records.

### Listing (luac.c print code)
- 5.4 `NEWTABLE`: `A B C ; C+EXTRAARGC` (no `k`, no `ivABC`); `SETLIST`: `A B C` plus `; C+EXTRAARGC` only if `k`; `VARARG`: `A C ; n out`; no `GETVARG`/`ERRNNIL`. Constant floats print with `%.14g` (LUA_NUMBER_FMT) in 5.4, `%.15g` in 5.5. `SHRI`/`SHLI` case order differs (irrelevant to output).

### Parser/codegen (lparser.c / lcode.c)
- Variable kinds: 5.4 `VDKREG=0, RDKCONST=1, RDKTOCLOSE=2, RDKCTC=3` (lparser.h:90-93) - these numbers are dumped in the upvalue `kind` byte, so they differ from 5.5 (`RDKVAVAR=2, RDKTOCLOSE=3, RDKCTC=4`, +globals). No `VVARGVAR/VGLOBAL/VVARGIND`, no `ind.ro/keystr`, no `PF_VATAB`, no `OP_GETVARG/OP_ERRNNIL`, no named varargs, no `global`.
- Limits: 5.4 checks `MAXVARS=200` in `new_localvar` (counting declared-but-inactive variables, "too many local variables"); 5.5 checks it in `adjustlocalvars` (`reglevel > MAXVARS`). 5.4 `luaK_checkstack` errors with `"function or expression needs too many registers"` when `newstack >= MAXREGS (255)`; 5.5 uses `luaY_checklimit(...,"registers")` ("too many registers (limit is 255) in ..."). 5.5 adds limit errors for `returns` and `multiple results` (5.5 lcode.c 215, 759); 5.4 has none. Nesting limit (`C stack overflow`, `LUAI_MAXCCALLS=200`) behaves the same: 198 nested `do` compile, 199 fail (measured in both references).
- Constants cache: 5.4 caches constant indices in **one table shared by all functions** of the chunk (`ls->h`; lcode.c:544 `addk` re-validates a hit with `k < fs->nk && same type tag && rawequal`); 5.5 gives each `FuncState` its own `kcache` (lcode.c:565 `k2proto`) and handles `0.0` via the FuncState pointer. 5.4 float keys: integral floats are keyed by `r + r*2^-52` (or `2^-52` for zero, so `0.0` and `-0.0` share one slot); 5.5 uses `r*(1+q)` and never reuses a constant if the key is still integral or collides. (The zero/collision quirks are replicated from the source; no listing in the corpus distinguishes them because zero floats normally go through `LOADF`.)
- `luaK_self` (5.4 lcode.c:1087): always `OP_SELF` via `codeABRK` (the method name may be a register or any constant, `k` flag); 5.5 emits `SELF` only for short-string constants and otherwise `MOVE`+`GETTABLE`.
- Table constructors: 5.4 `NEWTABLE A B C k` + `EXTRAARG` (array size split at `MAXARG_C+1`), `SETLIST` flush every `LFIELDS_PER_FLUSH=50` items; 5.5 uses `ivABC` (`vB/vC`, 10-bit `vC`) and `maxtostore` adaptive flush (lparser.c 1014-1029 in 5.5).
- Varargs: 5.4 `VARARGPREP nparams` (set in `setvararg(fs, nparams)`), `VARARG A 0 C`; `luaK_finish` patches `RETURN` `C = numparams+1` when `is_vararg`. 5.5 `VARARGPREP 0`, `VARARG A numparams C`, `PF_VAHID/PF_VATAB` handling.
- Loops: 5.4 numeric `for` uses 3 hidden `(for state)` locals + the (assignable) control variable and no `freereg--` after `FORPREP`; generic `for` has 4 hidden locals (`nvars = 5` incl. the index). 5.5: 2 hidden + **read-only** control variable (`RDKCONST`), generic: 3 hidden + read-only control, `forbody` does `fs->freereg--`. So `for i = 1,2 do i = 3 end` is legal in 5.4 and an error ("attempt to assign to const variable 'i'") in 5.5.
- `break`/`goto`: 5.4 `break` = `goto break`; the loop's `leaveblock` creates label `"break"` and may emit `CLOSE` (`createlabel`, lparser.c:608-624; `movegotosout` 628-639; `undefgoto` "break outside loop at line N"). Backward `goto` emits `CLOSE` + patched `JMP` immediately; forward `goto` is a bare `JMP`, and a `CLOSE` is added when the label is created (if some goto `close` flag is set). 5.5 emits `JMP` + placeholder `CLOSE` for every goto/break, resolves them in `leaveblock` (`solvegotos`, `closegoto` swap), checks `break` outside loops at the statement ("break outside loop" is a syntax error, with token), and messages say `jumps into the scope of '%s'` (5.4: `... of local '%s'`).
- `if cond then break end`: 5.4 `test_then_block` (lparser.c:1639) special-cases it (`luaK_goiffalse` makes the condition itself jump to the loop exit: `TEST; JMP exit`); 5.5 compiles it as a regular block (`TEST; JMP; JMP exit; CLOSE; ...`, observed for `while a do if b then break end end`).
- Statement order differences: 5.4 `funcstat` calls `check_readonly` after `body`; 5.5 before. 5.4 `body` emits `OP_CLOSURE` in the parent *before* `close_func` of the child (observable only through error ordering); 5.5 closes the child first. `repeat ... until` leaves the scope block first and then, if it had upvalues, emits the `CLOSE`-on-repeat fix-up (5.4 lparser.c:1488 `repeatstat`).
- `luaK_finish` (5.4 lcode.c:1847): only `RETURN0/1/RETURN/TAILCALL` + `JMP` threading; 5.5 adds `GETVARG/VARARG` rewriting.

## Standard-library cores and debug info 5.4.9 vs 5.5.1 (task A4; each item verified differentially against both reference binaries)
- **Identical** in both versions (same code, same results over the randomized corpora): Lua patterns (`match`/`find`/`gmatch`/`gsub`, `MAXCCALLS=200`, all error strings), `string.format` (incl. `%q`, `%a`, `%p`; `%F` is *not* a valid conversion in either), `os.date`/`os.time` (C99 `LUA_STRFTIMEOPTIONS`), `utf8.len/codepoint/char/codes`, the xoshiro256** generator and `project` (5.4's power-of-two shortcut gives the same values as 5.5's generic loop), `string.pack` option semantics.
- `string.pack/unpack/packsize` (`lstrlib.c`): **native max alignment** (`!` with no number, `offsetof(cD,u)`) is 16 in 5.5 (`LUAI_MAXALIGN` contains `long double`, luaconf.h:727) and 8 in 5.4 (`lua_Number n; double u; void *s; lua_Integer i; long l`), so `string.packsize("!I12")` is an error in 5.5 ("format asks for alignment not power of 2") but 12 in 5.4. Sizes are `int` in 5.4 (`getnum` stops at `(INT_MAX-9)/10`, largest `c` size 2147483639) and `size_t` with `MAX_SIZE` = `lua_Integer` max in 5.5. In 5.5 the "integral size (%d) out of limits" message prints the low 32 bits of a `size_t` (it passes a `size_t` to `%d`).
- `string.pack` pushes a `nil` marker above the arguments, so a *missing* argument is reported as `got nil` for the first absent index and `got no value` afterwards (both versions).
- `utf8.offset`: 5.5 returns **two** values (start and end byte position of the character; may raise "initial position is a continuation byte" after the search), 5.4 returns only the start.
- `math.randomseed()` without arguments: 5.5 seeds with `luaL_makeseed` and a draw from the old state (`n2 = nextrand`); 5.4 uses `time(NULL)` and the state address. Both return the two seed integers (`math.randomseed(n[, m])` returns `n, m` as `setseed` does). Explicit seeds reproduce the reference sequences exactly (`random()`, `random(m)`, `random(m,n)`, `random(0)`).
- Loader mode string (`checkmode`, ldo.c): the message prints the mode string exactly as given (`mode is 'tb'`). 5.5 additionally treats a `B` in the mode as "fixed buffer" binary chunk (C API only; Lua's `load` rejects it with `bad argument #3 to 'load' (invalid mode)`), which skips the binary check.
- `luaM_growvector` limits: `too many functions (limit is 131071)` (MAXARG_Bx) is checked when a function body *starts*, in both versions; `too many constants (limit is 33554431)` and `too many opcodes (limit is 2147483647)` are implemented but unreachable in practice (gigabytes of source); line-info vectors (INT_MAX) likewise.
- Debug naming (`ldebug.c`): 5.4 names the key of `OP_SELF` with `rkname` (constant or register), 5.5 with `kname` only; 5.5 handles `OP_GETVARG` like `OP_GETTABLE` and adds `luaG_errnnil` (`global 'x' already defined`); `OP_GETI` reports `field 'integer index'` in both (not `'?'`). `funcnamefromcode` and `varinfo` otherwise match.

## Runtime 5.4.9 vs 5.5.1 (Phase 6b; all VERIFIED against `ref/54` by the official suite, `vm_corpus`, `table_diff`, libs diffs)
Implemented as `cfg(rustynail_lua54)` arms in the shared code (the 5.5 code paths are unchanged).
- **Interpreter** (`lvm.c`, `vm_unsafe.rs`): numeric `for` keeps 4 slots (`ra` internal index, `ra+1` counter/limit, `ra+2` step, `ra+3` control copy; `forprep` sets `ra+3` before the limit check); generic `for` calls at `ra+4` with `ra..ra+2` copied, `TFORLOOP` copies `ra+4` back to `ra+2`, `TFORPREP` marks `ra+3` tbc without the 5.5 swap; `NEWTABLE`/`SETLIST` use `B`/`C` with `MAXARG_C+1` for the `EXTRAARG` multiplier; `SELF` takes an RK key (register or any string constant, long strings included); `VARARG` has no vararg-table form; `luaG_traceexec`'s `isIT` is `testITMode && B == 0` for every opcode.
- **`LUA_COMPAT_5_3`** (the reference build defines it): `LUA_COMPAT_LT_LE` — a missing `__le` falls back to `not __lt(b, a)` (`CIST_LEQ`, negated again in `luaV_finishOp` after a yield); `LUA_COMPAT_MATHLIB` (`math.pow/log10/cosh/sinh/tanh/atan2/frexp/ldexp`; `atan2` is the same C function as `atan`, so which name `pushglobalfuncname` reports depends on the string seed in the reference too).
- `__call` chains have no length limit in 5.4 (`tryfuncTM` grows the stack with `checkstackGCp`); 5.5's `'__call' chain too long` (`MAX_CCMT`) does not exist.
- `__close` methods always get a second (error) argument, `nil` without error (`prepcallclosemth` + `luaD_seterrorobj(LUA_OK)`).
- `luaG_addinfo` without source: `?:<line>:` with `-1` for stripped code (5.5: `?:?:`). `luaG_forerror` is "bad 'for' %s (number expected, got %s)" in 5.4.9 as in 5.5.
- `luaL_pushresult` copies the buffer into a regular (GC-counted) string; 5.5 creates an uncounted external string from the buffer box.
- **Tables** (`ltable.c`): `computesizes` (more than half of `1..2^i` used, 5.5 `arrayXhash`), `rehash` counts the array part always and adds no room for deleted entries; every non-dummy hash part has a `lastfree` pointer (5.5: only `>= 8` nodes, linear search below); `alimit` (kept in the hint slot, `BITRAS` = flag bit 7) with `luaH_getn`'s border logic **and `luaH_getint`'s side effect** (an integer access past the limit moves it: `#t` of tables with holes depends on the access history); `hash_search` without the randomized probing. `table_diff` (8931 dumps) is identical to `ref/54/build-seed0/refrun`.
- `table` library: `checktab` requires `__len` for strings too; `sort`'s random pivot is `rnd % (r4*2) + lo + r4` (no `^ lo ^ up`), seed from `clock`/`time` (ours: `make_seed`).
- `string.rep` with both strings empty really loops `n` times in 5.4 (5.5 returns at once); ours returns at once (no observable difference except time).
- `coroutine.close` requires its argument and refuses a running coroutine ("cannot close a running coroutine"); `require`'s message drops the prefix of searchers that return nothing.
- **GC API**: `collectgarbage` options `setpause`/`setstepmul` and `incremental(pause, stepmul, stepsize)`, `generational(minormul, majormul)`; `step(n)` adds `n` **Kbytes** of debt; parameters stored like `setgcparam` (`/4`, read back `*4`). Defaults `LUAI_GCPAUSE` 200, `LUAI_GCMUL` 100, `LUAI_GCSTEPSIZE` 13 (8 KB), `LUAI_GENMINORMUL` 20, `LUAI_GENMAJORMUL` 100.
- **GC control** (`lgc.c`; ours `gc/gen54.rs`, object-level code shared): 5.4 keeps a byte debt `GCdebt` and `GCestimate` (live bytes after the last cycle: set to the heap size at the atomic step, decreased by every sweep and string-table shrink); 5.5 keeps `GCmarked`/`GCmajorminor`. Incremental: 5.4 `incstep` converts debt and `2^stepsize` to work units (`/ WORK2MEM * stepmul`) and loops single steps until the credit is spent or the cycle ends (no stop after `atomic`); work = 5.4 traversal costs, sweep = objects visited (`GCSWEEPMAX` 100), finalizers 10 per step at 50 units; `setpause` = `estimate/100 * pause` (5.5: `applygcparam(PAUSE, marked)`). Generational: 5.4 has a single `KGC_GEN` kind; `genstep` does a minor collection and `setminordebt` (`total/100 * genminormul`) unless the debt is positive and memory grew more than `genmajormul`% over `GCestimate`, then a stop-the-world major `fullgen` (`enterinc` + `entergen`); if that frees less than half of the growth it is a "bad collection": `lastatomic` = atomic work, `setpause`, and later steps run `stepgenfull` (incremental kind, full atomic, back to generational only if the work is < 9/8 of `lastatomic`). `lua_gc` reports "generational" while `lastatomic != 0` (`isdecGCmodegen`). 5.5 instead runs major collections incrementally (`KGC_GENMAJOR`) with the `minormajor`/`majorminor` byte tests. `enterinc` (5.4) whitens all lists and goes to pause; 5.5 `minor2inc` enters the sweep phase. 5.4 `restart` sets the debt to 0, so the next allocation makes a step due.
- **C API**: `lua_newstate(f, ud)`; `LUA_REGISTRYINDEX = -LUAI_MAXSTACK - 1000` (-1001000), `LUA_RIDX_MAINTHREAD = 1`; GC option numbers `SETPAUSE 6, SETSTEPMUL 7, ISRUNNING 9, GEN 10, INC 11` with int varargs; `lua_resetthread` and `lua_setcstacklimit` (returns 200) are functions; `luaL_openlibs` is a function (linit order); no `lua_pushexternalstring`/`lua_numbertocstring`; `lua_Debug` has no `extraargs` and `unsigned short ftransfer/ntransfer`; `lua_pushfstring` raises "invalid option '%x' to 'lua_pushfstring'" for an unknown conversion; `luaL_Buffer` overflow says "buffer too large"; `lua_version` = 504.
